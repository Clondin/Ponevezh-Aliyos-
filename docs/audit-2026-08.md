# Site-wide Audit — Ponevez Kibbudim

**Date:** 2026-08-27
**Commit audited:** `ad65cec` (origin/main)
**Method:** Five parallel subsystem reviews (frontend, payments, storage/catalog, security/infra, email/ops), each finding cross-checked against source. All P0s independently verified in code. Baseline: `npm run check` passes clean (typecheck, calendar, transitions, D1, API contract + signed webhook, terminology).

**Legend:** ✅ = verified in code during this audit · 🔁 = found independently by two or more reviews.

---

## Summary

Code quality is high — server-authoritative pricing, a single-arbiter sold key, textbook webhook idempotency, HTML-escaped emails, strict input allowlists, no injection or PII leaks. The risk concentrates in two places: **race windows in the money path** and **the total absence of scheduled automation** — together, failures don't self-heal and a human must notice. Fix the four P0s and the deploy/automation gap before the Rosh Hashanah rush and this is a solid system.

Counts: **4 P0 · 20 P1 · ~30 P2.**

## P0 — Money or notifications lost silently

### P0-1 · Double-charge race + non-atomic cart sale ✅🔁
**Files:** `lib/banquest/card.ts:100-165`, `lib/storage/repository.ts:219-271`, `app/api/checkout/route.ts`
The hold is checked once *before* the charge; the Banquest call runs with `capture: true`; `markCheckoutGroupSold` sells items one at a time (`for (const order of orders) await persistOrder(order)`, `repository.ts:250`). If the 12-minute hold lapses mid-charge and another donor acquires the item — or any single item in a cart is already taken — `persistOrder`'s NX throws `AlreadyTakenError` **after the card is captured**. The donor is charged, no order is recorded, the route returns 409, and for a cart the earlier items are already sold while `checkout.status` never becomes "sold." No automatic void/refund.
**Fix direction:** make the group sale all-or-nothing (pre-claim all sold keys, roll back on any conflict); on a post-capture conflict, void the Banquest transaction and surface it to the office.

### P0-2 · Office never notified if `OFFICE_NOTIFY_EMAIL` unset — silently ✅
**Files:** `lib/notifications/email.ts:109-110, 217-219`; callers `app/api/webhook/banquest/route.ts:90`, `lib/banquest/card.ts:154`, `app/api/pledge/route.ts:53`
`notifyOfficeOfPledge`/`notifyOfficeOfOrder` throw at line 110 **before** the email record is written to the outbox, and every caller swallows the error with `console.error`. Nothing validates the var at startup (`payment-status` checks Resend, not this). Donor pays, gets a receipt, and the office hears nothing — no outbox row, nothing to retry. A 72-hour pledge can expire before anyone knows the donor exists.
**Fix direction:** build/queue the office record to the outbox even when the address is missing (or hard-fail startup if unset); never throw before persisting.

### P0-3 · Reconciliation self-disables on the first conflicted transaction ✅🔁
**File:** `lib/banquest/reconcile.ts:26-63`
The loop has no per-transaction try/catch. `markCheckoutGroupSold` throwing `AlreadyTakenError`/`HoldExpiredError` propagates out, aborts the whole run, and skips the audit write (`:65`). Because it pages newest-first, the same poison transaction blocks every future run — and this is the *only* recovery mechanism for the P0-1 and stuck-pending cases.
**Fix direction:** wrap each transaction in try/catch, record failures, continue the loop.

### P0-4 · A refund/void webhook reverses the ENTIRE multi-item payment ✅
**Files:** `app/api/webhook/banquest/route.ts:53-58, 68-76`, `lib/storage/repository.ts:273-301`
A `subType: "refund"`/`"void"` event runs `reverseCheckout`, which **hard-deletes all** `sold:` and `order:` records for the cart (physical delete, not a refunded flag). Refunding one kibbud of a 3-item charge in the Banquest dashboard puts all three back on sale and erases the order history.
**Fix direction:** scope reversal to the affected item(s); mark orders refunded rather than deleting them.

## P1 — Significant, fix soon

### Frontend / SEO

- **P1-1 · Every social/WhatsApp share preview 404s** ✅ — `app/layout.tsx:36`. `metadataBase` already carries `/high-holidays`; the `og:image` URL passes through `withBasePath` again → `…/high-holidays/high-holidays/images/social-card.jpg`. Fix: drop `withBasePath` for metadata URLs (they resolve against `metadataBase`).
- **P1-2 · Kibbud pages lose the social card** — `app/(site)/[minyan]/[occasion]/[kibbud]/page.tsx:31`. Page-level `openGraph` replaces the root object wholesale and sets no `images`.
- **P1-3 · `robots.txt` is invisible to crawlers** ✅ — `app/robots.ts`. Served at `/high-holidays/robots.txt` (basePath); crawlers only fetch `/robots.txt` at the domain root, so the admin disallow and the sitemap pointer are never read. Needs a root-host rewrite or coordination with the apex site.
- **P1-4 · Basket locks you out of your own hold** — `app/(site)/basket/page.tsx:15-16`, `components/CartCheckoutExperience.tsx:56, 201-216`. Any status row (including the visitor's own hold) marks an item `available:false`; reload mid-checkout → "Unavailable" badges + disabled button for up to 12 min, even though `/api/cart/hold` would re-attach the same cookie. The single-item flow gets this right (`[kibbud]/page.tsx:69`).
- **P1-5 · Lists show sold cards after cutoff; availability overstated** ✅🔁 — `app/(site)/[minyan]/[occasion]/page.tsx:41`, `[kibbud]/page.tsx:51` gate on `isWaveOpen` only, never `saleWindowFor(...) === "closed"` (cutoffISO), while `/find` does. After a tefillah's cutoff the grid still shows "Sponsor" cards that auto-fire `/api/hold` and fail. Separately `lib/availability.ts:41-54` never subtracts closed occasions, so home/minyan "NN available" and "From $X" overstate what's buyable.

### Payments / abuse

- **P1-6 · Checkout is a card-testing oracle** 🔁 — Turnstile is verified on `hold`/`cart/hold` but **not on `pledge` or either checkout** (`app/api/checkout/route.ts`, `app/api/cart/checkout/route.ts`); one hold permits unlimited retries (each decline runs `releaseCheckout`, freeing the token); decline messages are echoed verbatim (`card.ts:168-170`). Combined with the non-atomic limiter (P2), a single solved Turnstile enables looping stolen cards.
- **P1-7 · `/api/pledge` has no bot gate** 🔁 — `app/api/pledge/route.ts:20-54`. No Turnstile, no required hold; creates 72-hour inventory holds and sends donor+office email to attacker-supplied addresses, throttled only by a 5/hour non-atomic per-IP limit. Enables inventory-lock spam and outbound email amplification.
- **P1-8 · Phantom "pending" from a mid-charge crash** 🔁 — `lib/banquest/card.ts:55-61`. If the worker is evicted after `saveCheckout` but before the charge, the donor's retry finds status "created" and calls `markCheckoutPending` → item locked 7 days with **no charge ever sent**; reconcile can't free it (it iterates gateway transactions, which don't include this phantom). Undersell for up to 7 days.
- **P1-9 · `markCheckoutPending` clobbers a newer buyer's live hold** — `lib/storage/repository.ts:168-175`. Unconditionally overwrites `hold:{kibbudId}` with the old checkout's token + 7-day expiry, breaking a concurrent buyer's in-progress checkout ("hold expired").
- **P1-10 · `confirmPledgeGroup` partial-persist mishandled** — `repository.ts:408-451`, `app/api/admin/pledge/[id]/confirm/route.ts:19-24`. If one item of a multi-item pledge was sold meanwhile, the first order persists, the conflicting one throws, `pledge.status` never becomes "confirmed", and the route (catches only `HoldExpiredError`) 500s; re-confirming repeats the partial write.
- **P1-11 · `createPledge` partial-failure leaves a phantom pledge** — `repository.ts:303-372`. If a `pending`/`hold` set write fails after the pledge record + `pendingPledges` sadd, the catch releases holds but never deletes the pledge key or srems the set — a live, unexpired pledge with no reservation sits in the admin queue for 72h; confirming it later sells the item from under whoever holds it.

### Storage / performance

- **P1-12 · Availability query fan-out** ✅ — Home page issues **37 D1 queries per render** (force-dynamic, every view); minyan page 6-7; `/find` runs `statuses()` over all 358 items = 12 chunks awaited **sequentially** (`d1.ts:46-56`, a for-loop, not `batch`) = 12 serial round trips per render. One batched `statuses()` call could serve the whole home page.
- **P1-13 · `app_kv` grows without bound** ✅🔁 — Expired rows are filtered on read but never deleted (`lib/storage/d1.ts`); no cron. Rate-limit buckets (`rate:{action}:{ip}:{bucket}`, ~144/day/IP for hold alone), expired holds, checkout-attempt locks, and 90-day-TTL checkout records all become immortal dead rows.
- **P1-14 · Unbounded audit log, read in full** — `repository.ts:617-630`, `keys.ts:22`. Every hold/payment/pledge writes an audit row; `auditRecords()` does `smembers` of the entire set, sorts all ids in JS, then slices 200. `/admin/activity` pulls tens of thousands of rows per view after a busy season.
- **P1-15 · Sale-wave defaults fail open** — `lib/calendar/sales.ts:3-6`. Both waves default to `2026-08-25` while the contract says wave 1 opens 6 Sep, wave 2 opens 16 Sep. If `WAVE_2_OPENS_AT` is unset in prod, Hoshana Rabbah / Simchas Torah kibbudim become purchasable ~3 weeks early, with no warning. Also: a value without a UTC offset parses as UTC on Workers (4h early for ET midnight), and an unparseable value throws a site-wide 500 from both occasion pages.

### Security / infra

- **P1-16 · No automation of any kind** ✅🔁 — No `triggers` in `wrangler.jsonc`, no scheduled handler. Queued emails retry only by an admin click; reconcile runs only by a button; expired rows are never purged (P1-13). If Resend is down for an hour pre-Rosh Hashanah, every receipt sits queued until a human notices.
- **P1-17 · Admin sessions cannot be revoked** — `lib/api/admin-session.ts:33-54`, `app/api/admin/logout/route.ts`. Stateless HMAC token; logout only sets `maxAge:0` on the response cookie. A captured session stays valid the full 12h; the only kill switch is rotating the secret (logs out everyone).
- **P1-18 · `unsafe-inline` scripts in production CSP** — `next.config.mjs:19`. No nonce/hash, so CSP provides no mitigation for any injected inline script. Standard Next limitation; move to a nonce policy for a payment site.

### Email / ops

- **P1-19 · Manual recovery scripts broken by the basePath move** ✅ — `scripts/reconcile-banquest.ts:10` and `scripts/exercise-live-transitions.ts:5,38` drop the `/high-holidays` prefix; `npm run reconcile` and `npm run test:live` hit the legacy root site and fail with misleading errors (broken since commit `5aed905`).
- **P1-20 · CSV export unusable by the office** — `app/api/admin/orders.csv/route.ts:57-63`. Emitted UTF-8 with no BOM → Hebrew names become mojibake in Excel on Windows (the default double-click path). And there is **no UI link** anywhere to reach it; the office would have to hand-type the URL.

- `lib/api/rate-limit.ts:27-35` — counter is a non-atomic read-then-write; concurrent requests can exceed the limit; costs 2 D1 round trips per call. Fixed windows allow ~2× the limit across a bucket boundary.
- `lib/api/turnstile.ts:39` — action check is `result.action && result.action !== expected`, so a response with no action field passes; unset `TURNSTILE_SECRET_KEY` silently no-ops (fail-open).
- `lib/api/auth.ts:11` — API-token path uses non-constant-time `===` (the cookie path uses `constantTimeEqual`); `ADMIN_TOKEN` doubles as login password and API bearer (no interactive/programmatic separation).
- `lib/banquest/client.ts:64-69`, `card.ts:27-38` — `ALLOW_SANDBOX_CHECKOUT` / `BANQUEST_SANDBOX_AMOUNT_USD` ship in prod builds; a two-env-var mistake (`BANQUEST_ENV=sandbox` + `ALLOW_SANDBOX_CHECKOUT=true`) marks real inventory sold against fake-money charges.
- `lib/banquest/reconcile.ts:26-63` — pages the **entire** Banquest history every run (no date filter), re-reverses already-reversed checkouts (appending phantom `payment_reversed` audit rows), and inflates the `updated` counter; hundreds of subrequests per click months in.
- `lib/banquest/reconcile.ts:54` — reconcile never calls the Admire sync; a payment recovered via reconcile (the exact webhook-missed case) never reaches the Admire CRM.
- `app/api/webhook/banquest/route.ts:44-45` — a concurrent duplicate that finds the lock "busy" is ACKed 200 while the holder may still fail; if Banquest tracked only that delivery, the event is dropped until manual reconcile. Done-marker written with no TTL.
- `app/api/webhook/banquest/route.ts:77-83` — underpayment branch only `console.error`s and parks the item pending 7 days; no office email, no reversal.
- `app/api/checkout/route.ts:32` — single-item checkout accepts a cart cookie (`holdCookie.kibbudId` = cart's first item), so a 3-item cart can be charged for item 1 alone, locking the other two under a now-consumed token.

- `lib/storage/memory.ts:38` vs `d1.ts:67` — `ex:0` means "no expiry" in memory but "already expired" in D1.
- `lib/storage/client.ts:15-20` — memory fallback gated only on `NODE_ENV !== "production"`; a preview/staging runtime without that value silently swaps in a per-isolate store (oversell possible there).

## Genuinely well built

- **Amount integrity is airtight** — clients never send amounts; prices resolve server-side from the catalog via `trustedAmount`; the webhook cross-checks the gateway-reported amount.
- **The sold key is a single atomic NX arbiter** every sale path (card, webhook, pledge, reconcile) must pass — true double-sold state is impossible.
- **Webhook security is textbook** — HMAC-SHA256 with `timingSafeEqual`, strict hex validation, fail-closed when the key is unset, event-ID dedup with a lock/done two-phase claim, and a replay test.
- **Email delivery is idempotent three ways** — stable per-order IDs, a sent-status check, and Resend idempotency keys; every user field is HTML-escaped.
- **Ambiguous gateway failures keep the item pending** (not released, not sold) to avoid double-sale, with a comment explaining why, and a proven double-submit lock.
- **D1 NX emulation** reclaims an expired row atomically in one conditional upsert; proven single-winner under 8-way concurrency by `test-d1-store.ts`.
- **Strict positive input validation** — every payload rejects unknown fields and bounds lengths.
- **CSV formula-injection defense**, consistent clickjacking policy (`frame-ancestors 'none'` + `X-Frame-Options: DENY`), full HSTS/nosniff/Permissions-Policy, and Admire cleanly retired (410 tombstone, no CSP residue).
- **Dual catalog is now byte-identical** (fixture vs generated) — the earlier drift concern is resolved.
- **The catalog generator** is deterministic, committed at build time, self-guarding against Hebcal drift, with a 10-year snapshot pin and face-value checksums.

## Suggested sequencing

1. **The four P0s** — atomic/all-or-nothing group sale with a void on post-capture conflict (P0-1); fail-safe office-notify to the outbox (P0-2); per-transaction try/catch in reconcile (P0-3); scope refund reversal to the affected item (P0-4).
2. **Deploy + automation gap** — a scheduled Worker for outbox-drain, reconcile, and expired-row purge; plus a GitHub Action to deploy `main`.
3. **Cheap high-value UX/SEO** — og:image (P1-1/2), robots (P1-3), basket own-hold (P1-4), cutoff-aware lists + availability (P1-5), batched availability query (P1-12).
4. **Security hardening** — Turnstile on pledge/checkout (P1-6/7), admin session revocation (P1-17), nonce CSP (P1-18).
5. **P2 sweep** — dead code, consistency, a11y, doc drift.
